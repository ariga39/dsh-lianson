# Development Plan: Orchestrating DeepSeek Harness (`dsh`) from Codex

> **Status**: Finalized implementation plan corresponding to [requirements.md](requirements.md) and [design-brief.md](design-brief.md) (design only; no source code changes in this phase).
> **Upstream baseline**: DeepSeek Harness commit [`4b399c39a6d1479cd84ca591b4d7c88e24d38a96`](https://github.com/deepseek-ai/deepseek-harness/tree/4b399c39a6d1479cd84ca591b4d7c88e24d38a96) (`0.2.3-alpha.2`, 2026-11-22). ## 1. Architecture Decisions and Boundaries

### 1.1 Observed Facts and Recommended Architecture

1. **Capability benchmark**: At commit `4b399c39a6d1479cd84ca591b4d7c88e24d38a96`, upstream ships no native TUI application or `tui` profile; the official profiles are `web`, `headless`, `sdk`, `sdk-minimal`, and `acp` ([`docs/architecture.md`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/docs/architecture.md#L17-L43)). Complete interactive human session capabilities live in the `web` profile (Host `SessionController` + `TypertGateway` + `dsh-web-app`), which this plan uses as the benchmark.
2. **Recommended architecture (zero upstream modifications)**:
   - **Sole session and write-lock owner**: One persistent `dsh web --no-open --host 127.0.0.1 --port <port>` Host process holding in-memory `ctx.agents`/`ctx.sessions` and the cross-process exclusive `session.lock` lease ([`packages/session/session-persistence-jsonl/src/lease.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/session/session-persistence-jsonl/src/lease.ts#L70-L116)).
   - **External orchestration layer (`dsh-liaison`)**: A thin persistent answering operator plus an idempotent CLI. The operator exchanges the Host launch token via `GET /connect?token=<launchToken>&interactions=answer` for a v2 cookie, maintains the single `/api/remote.mux` WebSocket and `$events` stream ([`packages/host/authentication-token/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/host/authentication-token/src/index.ts#L74-L111), [`browser-auth.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/host/authentication-token/src/browser-auth.ts)), and serves short Codex commands over a user-only local IPC socket.
   - **Browser viewing surface**: A user can open the same `dsh web` instance at any time (v1 cookie), locate the exact session by workspace and unique task title, and attach to both persisted history and the in-process `agent/assistant-stream` ([`packages/api/session-controller/src/web/controller.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/web/controller.ts#L32-L77)). Closing the browser page only drops the browser stream; it neither stops the Host agent nor cancels pending questions or approvals.
3. **Why other entry points are excluded**:
   - **SDK (`dsh --profile sdk`)**: Spawns a private runtime subprocess that exclusively holds `session.lock`, conflicting with `dsh web` (`session/writer-held` on activation, [`packages/api/session-controller/src/agent.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/agent.ts#L200-L202)), and its protocol lacks `steer`, `updateQueue`, wire `cancel`, and per-session `selectModel` ([`packages/sdk/protocol/src/types.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/sdk/protocol/src/types.ts#L216-L225), [`packages/sdk/client/src/client.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/sdk/client/src/client.ts#L188-L190)).
   - **Headless (`dsh headless`)**: Exits after a single turn, provides no `steer` or interactive channel, and explicitly refuses to take over Web sessions that carry an `agentPreset` ([`packages/bundle/headless/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/bundle/headless/src/index.ts#L221-L230)).
   - **ACP (`dsh --profile acp`)**: Private subprocess holding `session.lock`, no Web server, and no `steer`, `updateQueue`, or `user-questions` ([`packages/acp/acp/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/acp/acp/src/index.ts#L1-L10), [`L155-L176`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/acp/acp/src/index.ts#L155-L176)).
   - **Stateless short-lived CLI calling `/connect` per command**: `apiPeers` entries are only cleaned up when the `/api/remote.mux` WebSocket closes or the plugin disposes ([`packages/host/authentication-token/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/host/authentication-token/src/index.ts#L74-L75), [`L111`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/host/authentication-token/src/index.ts#L111)). Connecting without holding a WebSocket leaks peers, and without a persistent `$events` subscriber no external operator can answer questions or approvals when no browser is open.

### 1.2 Minimal Ownership Split

- **Herdr**: Hosts the primary Codex session, stores private task handoffs (recording stable session addresses, revisions, and review status), and hosts independent review sessions as needed; adds no dsh-specific PTY adapter.
- **Upstream `dsh`**: **Zero code changes** in MVP. Because the Web UI currently has no `?session=<id>` deep link (selection is stored only in `localStorage['dsh.sessions.current']`, [`packages/client/ui-workspace/src/client/navigation.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/client/ui-workspace/src/client/navigation.ts#L175-L177)), MVP locates sessions via `workspace/create` plus a unique task title rather than modifying the frontend.
- **This project (`dsh-liaison`)**: Builds only the minimal orchestration adapter—reusing upstream Node client, mux, and typed remote packages, and implementing only the missing pieces.

## 2. Key Protocol Semantics, Side Effects, and Concurrency Boundaries

### 2.1 Session Creation (`create`): Partial Success, Concurrency, and Dropped Responses

Based on [`packages/api/session-controller/src/agent.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/agent.ts#L214-L234), [`L332-L381`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/agent.ts#L332-L381), and [`packages/api/session-controller/src/commands.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/commands.ts#L120-L159):

1. **Write-ahead ledger before RPC**: Mint a fresh `sessionId = "session-<uuid>"` for each new delegation and persist it to the ledger (`state: 'creating'`) before calling `session.create({ workspaceId, sessionId, agentPreset })`.
2. **Dropped-response retries and concurrency**: The Host serializes concurrent creates for the same `sessionId` via `inOrder`. If the initial create succeeded on the Host but the HTTP response was lost, retrying with identical parameters idempotently reclaims that session via `claim()` as long as it is still empty, matches `cwd` and `workspaceId`, is unarchived, and is not write-locked elsewhere.
3. **True identity-conflict semantics (hard guard against session substitution)**:
   - Mismatched `cwd` → Host throws `session/conflict`;
   - Target is a subagent session → Host throws `session/agent-busy`;
   - Target has already started a turn (non-empty), is archived, belongs to another `workspaceId`, or is write-locked elsewhere → **the Host does not throw; it silently mints and returns a different `sessionId`** ([`packages/api/session-controller/src/agent.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/agent.ts#L365-L380)). Clients **must** assert `returned.sessionId === requested.sessionId` and reject the binding on mismatch.
4. **Partial-success semantics**: If `agents.create` succeeds but `workspace.attachSession` fails, the Host throws `session/workspace-attach-failed` with `details: { sessionId, workspaceId }` ([`packages/api/session-controller/src/commands.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/commands.ts#L151-L156)). Because the session already exists as an ungrouped session, the ledger must retain that `sessionId` and surface an explicit error rather than blindly creating a second orphan session.

### 2.2 Global Side Effect of `selectModel` and Per-Session Verification

- **Side effect**: After recording the session-level selection, `session.selectModel` asynchronously invokes `agentDefaultModel.saveSelection(selected)` ([`packages/api/session-controller/src/commands.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/commands.ts#L180-L184)). This **mutates the Host's global default model**, affecting newly created sessions and existing sessions that have not yet recorded their own `model/selected` event (which read the default dynamically via getter, [`packages/api/session-controller/src/agent.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/agent.ts#L468-L476)).
- **Isolation and verification rules**:
  1. Call `session.modelCatalog()` before session creation to verify the target `provider`/`model`/`reasoningEffort` is routable;
  2. Call `session.selectModel` **explicitly for every delegation** and verify the returned `selected` value—never rely on the global default;
  3. After the first turn submits, verify the actual model request from the session's persisted `request/header` event at `event.data.header.config` (`provider`, `model`, `reasoningEffort`, [`packages/core/session/src/types.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/core/session/src/types.ts#L256-L258), [`L405-L409`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/core/session/src/types.ts#L405-L409)).

### 2.3 Authorization, Approvals, and Questions (Codex Adjudicates in MVP)

- **No generic policy engine**: In MVP, `dsh-liaison` only receives, buffers, and relays interaction requests and responses. **Codex makes every concrete decision within the user's existing authorization** and escalates to the user when a request exceeds that authorization.
- **Strict isolation of unbound sessions**: Only `approval/request` and `user-questions/request` events belonging to bound delegations enter the pending table and cause `session/wait` to return `reason: 'input-required'`. Unbound sessions always receive `{ kind: 'next' }` and are never answered by `dsh-liaison`.
- **Fail closed on unclear requests**:
  - `approval/request` carries `toolName`, optional `callId`, and `reason`/`displayReason`, without tool arguments ([`packages/interaction/user-approval/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/interaction/user-approval/src/index.ts#L126-L145)). Although `tool/call` normally persists before `tools/pre-execute` ([`docs/architecture.md`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/docs/architecture.md#L105)), **`callId` may be missing and arguments may become visible later or remain unresolvable**. `dsh-liaison` attempts to resolve recent `tool/call` context by `callId` for Codex, but any request whose action cannot be clearly identified or exceeds explicit authorization **must never be auto-approved** (keep pending for explicit Codex `reject` or user escalation).
  - `user-questions/request` (covering both `ask_user_question` and `exit_plan_mode`'s `plan-review` intent, [`packages/plan/plan-mode/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/plan/plan-mode/src/index.ts#L338-L355)) stays pending until Codex invokes `answer` with `{ answers }`. If a session uses `timed` mode and transitions to `continued` on timeout, deliver the late answer via `userQuestions/answer` (wire arguments `agentId`, `callId`, `answer`, [`packages/interaction/user-questions/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/interaction/user-questions/src/index.ts#L187-L232)).
- **Browser open/close during pending interactions and resolution races**:
  - [`packages/api/gateway/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/gateway/src/index.ts#L564-L566), [`L711-L739`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/gateway/src/index.ts#L711-L739) show that a newly connected answering client immediately receives all current `pendingRemoteEvents`; closing the browser only removes that browser's delivery and **does not cancel or settle pending questions or approvals**. Once any client submits a valid outcome, the Gateway broadcasts `{ type: 'cancel', eventId }` to remaining clients (aborting the corresponding listener `signal`).

### 2.4 Mid-Run Steering (`steer`), Stopping (`stop`), and In-Place Rework

- **Acceptance vs. verification**: `session.prompt({ requestId, sessionId, mode, content })` returning `{ accepted: true }` proves only that the message was accepted (or deduplicated by `requestId`, [`packages/api/session-controller/src/commands.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/commands.ts#L325), [`L392-L415`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/commands.ts#L392-L415)), not that the work succeeded. `session.wait` returning `idle` means only that the turn went quiet; **Codex must independently inspect code, tests, and observation artifacts before accepting**.
- **Mid-run steering**: Send `session.prompt(mode: 'steer')` to inject into `nextStep`. To edit, delete, or promote queued items, read `session.state().queue` and call `session.updateQueue(edit | remove | steer)` (promoting to `steer` is valid only for `next-turn` items while `running`, otherwise the Host returns `session/steer-unavailable`).
- **True boundary of `stop`**:
  - `session.cancel` calls `agent.cancel({ kind: 'user' }, { keepInbox: true })` ([`packages/api/session-controller/src/commands.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/commands.ts#L540)). [`packages/core/agent-loop/src/agent.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/core/agent-loop/src/agent.ts#L189-L199), [`L278-L282`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/core/agent-loop/src/agent.ts#L278-L282) confirm that `keepInbox: true` neither clears `inbox` nor clears `wakeRequested`: after the active turn ends with `turn/end` `reason: { kind: 'aborted', reason: { kind: 'user' } }` ([`L402`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/core/agent-loop/src/agent.ts#L402)), any remaining queued item immediately starts a new turn.
  - Therefore `dsh-liaison stop` must run a **bounded cleanup loop** (default max 3 rounds): (1) read `state.queue` and call `updateQueue(remove)` on each item (tolerating `session/queue-item-not-found` from concurrent dequeue); (2) call `session.cancel` (tolerating `session/not-found` if already cold/idle); (3) call `session.wait` to verify `running === false && (queue === null || queue.length === 0)`. If concurrent external input (e.g., from a browser) leaves residual queued items, or a misbehaving tool ignores `AbortSignal` until timeout, **`stop` must explicitly report non-quiescence and residual queue details rather than claiming an atomic halt**.
- **In-place rework and cold recovery**: Submit `session.prompt(mode: 'queue')` to the same `sessionId` to continue with existing context. Even after a `dsh web` restart, the Host reloads persisted logs and preset via `resolveAgent` ([`packages/api/session-controller/src/agent.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/agent.ts#L285-L319)). If a session was archived (`ArchivedSessionGate` blocks new steps), call `workspace.unarchiveSession` before sending follow-up instructions.
- **Protocol quick reference**:
  - Event `seq` starts at `0` with step `1`; an empty session has `cursor === -1`. During `session.create`, `permissionPresets` writes `permission/preset`, `sandbox/mode`, and `approval/policy` on `agent/created` ([`packages/interaction/permission-presets/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/interaction/permission-presets/src/index.ts#L241-L243), [`L510-L517`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/interaction/permission-presets/src/index.ts#L510-L517)), so **the first `user/message` does not have `seq === 0`**. Verify incremental contiguity over `[beforeCursor + 1 .. finalCursor]` relative to the cursor captured before submitting.
  - `session.wait` defaults to a 30s timeout and polls `pendingInput` every 1s ([`packages/api/session-controller/src/state/controller.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/state/controller.ts#L18), [`L72`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/state/controller.ts#L72)); its `output` includes only `assistant/message` entries ([`packages/api/session-controller/src/history/controller.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/session-controller/src/history/controller.ts#L126-L143)) and waits only on the root agent (not background subagent trees). Pair it with `session.events` for full tool calls/results and `session.projections` for `subagentCatalog`.
  - Wire naming (for debugging or bypassing generated proxies): single-object RPCs wrap `{ args: { request: ... } }`; `agent: Agent` parameters serialize as `agentId` carrying `sessionId` ([`packages/core/agent/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/core/agent/src/index.ts#L273-L276)); `$events/result` sends `{ args: { clientId, eventId, outcome } }`.

## 3. Early Vertical Slice (Slice 0): Minimal Falsifiable Keyless E2E

**Principle**: Before writing the full daemon, reconnect state machine, or CLI wrapper, run a minimal script reusing upstream Node client packages (matching [`authenticated-node.client.spec.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/api/gateway/tests/authenticated-node.client.spec.ts)) to falsify core architectural assumptions immediately.

### 3.1 Scenario and Gating (Keyless, Zero Model Spend)

1. **Setup**: Create a temporary `DSH_HOME` and target test workspace `cwd`. Launch a real `dsh web --no-open --host 127.0.0.1 --port 0` with `--patch` mounting a local scripted Mock LLM (following [`packages/test-support/llm-mock-server`](https://github.com/deepseek-ai/deepseek-harness/tree/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/test-support/llm-mock-server) and [`apps/web/tests/scaffold.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/apps/web/tests/scaffold.ts)).
2. **External prompt submission (no browser)**: Connect a minimal Node operator via `/connect?token=...&interactions=answer` and execute `workspace.create({ path: cwd })` → `session.create({ workspaceId, sessionId: mintedId })` → `session.rename({ sessionId, title })` → `session.selectModel(...)` → record `beforeCursor` → submit `session.prompt(mode: 'queue')` with a fixed `requestId`.
   - The Mock LLM executes 3 gated steps: Step 1 invokes `tool-fs`/`tool-bash` to persist a real `tool/call` + `tool/result`; Step 2 invokes `ask_user_question` to raise one pending question; Step 3 receives the answer, streams a final reply containing a sentinel token, and completes the turn.
3. **Duplicate submission check**: Resend `session.prompt` with the exact same `requestId` both while Step 1 is in flight and after Step 1 persists; assert both return `{ accepted: true }`.
4. **Mid-turn browser join (including pending-question window)**:
   - Once Step 2 triggers `user-questions/request` (`session.wait` returns `reason: 'input-required'` with `'question'` in `pendingInput`), launch Playwright Chromium, authenticate against the same `dsh web`, and open the session by workspace + unique title.
   - **Assert session identity and history visibility**: Verify the selected `sessionId` (`localStorage['dsh.sessions.current']` or `Copy session ID`) equals `mintedId`; verify the page displays the original prompt (count === 1), Step 1 tool call and result, and the pending question card.
   - **Critical sub-check (closing the browser while a question is pending)**: **Do not answer in the browser.** Observe live state, then **close the page and Chromium process**. Next, answer the pending question externally from the Node operator (`{ answers: [...] }`) to release Step 3.
   - Add a companion check during Step 3 streaming: open the browser mid-stream to observe `[data-streaming="true"]` live progress, then close the browser and verify the turn still completes and persists.
5. **Final reconciliation**: External `session.wait({ sessionId, afterSeq: beforeCursor })` returns `reason: 'idle'`. Fetch full `session.events({ address: { kind: 'session', sessionId } })` and assert:
   - `seq` contiguously covers `[0..finalCursor]` with no gaps and no duplicates;
   - Exactly one `user/message` carries `source.rpcId === requestId`;
   - `request/header` has `data.header.config` matching the selected model;
   - Complete event closure: `turn/start` → `user/message` → `tool/call` → `tool/result` → `ask_user_question` exchange → final `assistant/message` → `turn/end(completed)`;
   - Zero Playwright `pageErrors` and zero `session/writer-held` errors throughout.

### 3.2 Falsification Triggers (Stop and Revise Design If Any Fires)

- **F1**: Opening the externally created session in Web returns `session/writer-held`, or the new workspace/session is invisible without manual refresh.
- **F2**: Closing the browser while a question is pending cancels or breaks the `user-questions/request`.
- **F3**: Closing the browser causes the active turn to terminate with `aborted`.
- **F4**: Retrying with the same `requestId` persists two `user/message` entries (which would require a client-side single-flight lock in the ledger).

## 5. Acceptance Plan: Historical Routing Exercise (`compte-rendu #401`)

Strictly separate **repeatable local rehearsal** from **real deliverable acceptance** so mock green tests never substitute for real-world verification.

### 5.1 Reference Dependency Chain and 138-Observation Routing Contract

- **Dependency chain**: Baseline revision → Delegation A (production routing change producing revision `revA`, with review rework producing `revA2`) → Delegation B (test migration branched from `revA` and realigned to `revA2` after A's rework).
- **138-observation routing contract**: **23 paths × 3 HTTP methods (`GET`, `POST`, `DELETE`) × 2 authentication states = 138 observations**, comparing **HTTP status code, response body, `Cache-Control`, and `Content-Type`** on every item.
- **Live regeneration requirement**: Acceptance must capture the 138 observations live against both the baseline revision and the final revised deliverable (requiring 138/138 exact match), rather than comparing against pre-recorded files.

### 5.2 Repeatable Local Rehearsal (Keyless, Regression-Ready)

Using a temporary local git repository (containing baseline routes, test suite, and a standalone 138-observation capture script) with Mock LLM + real `dsh web` + `dsh-liaison` + Playwright:

1. **Dependent delegations**: Create worktree A from the baseline revision and delegate session A (`[routing] Production route refactor`) to produce commit `revA`. Codex verifies the diff, unit tests, and baseline vs. `revA` 138-observation diff. Create an independent worktree B from `revA` and delegate session B (`[routing] Test migration`).
2. **Parallel tracking and simulated review rework**:
   - While session A undergoes simulated review, Codex continues supervising session B and executes at least one mid-run `steer`;
   - Simulated review reports a concrete defect in A → Codex sends the findings back to **original session A** (asserting identical `sessionId` and preserved first-turn context), producing `revA2`;
   - **Dependency realignment**: Because B depends on A, Codex realigns worktree B (rebase/merge) onto `revA2`, notifies **original session B** of the updated base, re-verifies the test migration, and re-runs the 138-observation diff on the merged result (138/138 match).
3. **Dual paths (Web viewer and unattended)**:
   - Path 1 (with Web): Playwright opens `[routing] Test migration` (session B) mid-run, verifies the assigned prompt, inspected callers, executed tests, and results are visible, then closes the browser during a pending question or streaming output and confirms completion;
   - Path 2 (without Web): Executes the identical end-to-end flow with zero browser involvement and zero user intervention.

### 5.3 Real Deliverable Acceptance (Real Model, Repository, and Review)

Does **not** require reopening any previously merged PR; run either on a fresh branch created from the historical baseline revision or on an equivalent live two-delegation task:

1. **Executor and model verification**: Confirm both delegations' `selectModel` return values and persisted `request/header.data.header.config` match the agreed model with no silent fallback.
2. **Real changes and live 138-observation capture**: Codex independently regenerates the `23 paths × 3 methods × 2 auth states` captures on both the baseline and final revisions, diffs HTTP status, response body, `Cache-Control`, and `Content-Type` (138/138 match), and records the result bound to the final commit SHA.
3. **Agreed review tracking**: Follow the agreed online PR review (or independent review session) for delegation A while advancing delegation B in parallel; send real review findings back to the original session responsible for that deliverable, realign the downstream worktree if needed, and re-verify.
4. **Unattended completion and optional viewing**: The user does **not** need to appear or open Web at any point for the workflow (session creation → Codex-adjudicated questions/approvals within authorization → verification and delivery) to complete. If the user opens `dsh web` mid-run to inspect the test-migration session and closes it, execution continues unaffected and Codex spends zero tokens summarizing for the viewer.
